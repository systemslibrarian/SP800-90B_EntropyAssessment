## predictors

Headline result: F10 (MultiMMC's chained prefix lookup, multi_mmc_test.h:236/:93, inherited from upstream) is now CONFIRMED BY EXECUTION at the shipped constants. SP 800-90B 6.3.9 step 4.b.i requires an independent lookup of M_d at every depth; the code only looks up depth d if depth d-1 hit. The maxEntries=100000 cap breaks the implication the code's comment relies on: with data whose (d+2)-grams are all new, entries[d] = i-d-1, so depth d fills exactly one round before depth d+1 and in that single round one context is refused by M[d] while the longer context is accepted by M[d+1]; every later recurrence of that context suppresses all depth >= d predictions. Two 1,000,000-sample 8-bit fixtures I built show both error directions through an ordinary `ea_non_iid -i -a -vv <file> 8` run: f10_exploit_8bit_1M gives tool C=809998 r=19 H=0.30220817363257124 against the spec reference's C=765068 r=18 H=0.38427943464183960 (tool 0.082 bit low), and f10_over_8bit_1M gives tool C=741174 H=0.42991859516826059 against 741364 / 0.42954989344841465 (tool 0.00037 bit HIGH, i.e. an overestimate). A chained/unchained pair of spec simulators reproduces the tool's C and r exactly in both files, which pins the divergence to that one line; binary data is structurally immune (depth d holds at most 2^(d+2) pairs, so only d=15 can cap and it has no d+1), which is why the earlier 10-fixture binary-vs-generic differential came out identical. The same fixtures also show the F09 repair is live and material (upstream r=808737 / H=9.67e-06 vs master r=19 / H=0.302).
