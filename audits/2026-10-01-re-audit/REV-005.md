# REV-005 — PARTIALLY SUPPORTED (precise subclaims below)

Historical source: `34fb906196f8d47da774c88928eff0d8ec08d618`; current `328ec20c146e43b4eed86424847a106539c70a5a` has the identical guard script and estimator implementation. Full relevant script/compression source was read before execution.

## Infrastructure portability: CONFIRMED

cpp/selftest/regression-estimator-guards.sh invokes `clang++` directly, with Apple-Clang `-Xpreprocessor -fopenmp`, fixed `/opt/homebrew` include/library paths, and `-lomp`. It does not select an available GCC compiler for its ASan build.

- Probe 019: complete **unchanged native macOS** script passes, exit 0, 3.126 s, default ASan settings and two OpenMP threads. It computes compression exactly `0.15932269772157773`.
- Probe 020: complete **unchanged Linux** script cannot build, exit 2, 0.280 s: `clang++: command not found`. This is a test-infrastructure failure, not an estimator failure. Linux already has all dependencies required by the ordinary GCC build; the script assumes a different compiler/runtime layout.
- Probe 022: compiler-only adapter replaces Clang with GCC, removes Apple preprocessor/Homebrew/library flags, keeps OpenMP and ASan, and adds disclosed `-include climits`. Exact actual compiler commands are in logs/gcc-adapter.jsonl. Assertions, tolerances and input generation are unchanged.

## Linux sanitizer qualification: BLOCKED, not a pass

The adapted ASan suite exits 1 with seven failed checks, and several child processes exit 137 before producing estimator output. Probe 027 independently compiles a trivial correct ASan program. Under the same 3-GiB emulated x86-64 container it is killed by signal 9 before main, both with default options and with `ASAN_OPTIONS=detect_leaks=0`. The cgroup `oom_kill` counter increases by one each time. Disabling leak checking does not resolve this local resource/emulation limitation.

Therefore the prior review's **full adapted sanitizer-script failure solely at the numeric comparison** was not completely replayed here. This does not refute its Linux-native result. No safety check is marked passing on the basis of these killed processes. In particular, the script prints “no sanitizer error,” “no abort (exit 137),” and “clean” for some killed children because it checks selected strings/statuses rather than successful execution. The **whole script still fails**; those individual messages must not be quoted as sanitizer-clean evidence.

Captured fixtures, source and internal build logs are under captured/022-linux-guard-suite-gcc-adapter, with byte lengths, alphabets, widths and SHA-256 in CAPTURE-MANIFEST.json. No original script/fixture was weakened to obtain a pass.

## Exact-number portability: independently reproduced

The full non-sanitized GCC 13.3 assessment in probe 029 computes, rather than hard-codes:

- Literal compression: **0.15932269772157898**.
- The unchanged guard script requires exact string **0.15932269772157773**.
- Absolute difference: **1.25e-15**; relative difference: **7.845711991297...e-15**.
- The exact comparison is false (probe 030).

Fixture: NIST public ringOsc-nist, 1,000,000 one-byte binary samples, alphabet {0,1}, inferred width 1, SHA-256 `7d37dc3795e9b2927beb779008d7f4b4630dd7f2c058a2b14cee9d41a658dd68`. Full ten-estimator output is preserved, including the binding collision estimate/final value `0.12644573619604868`. The numerical discrepancy is exactly the one the previous review reported, but this standalone non-sanitized observation is **not** a full adapted guard-suite pass.

Native macOS long double: 8 bytes, **53 significand bits** (not “64 significand bits”), exponent limit 1024. Linux x86-64 userland long double: 16-byte storage, 64 significand bits, exponent limit 16384. The two representations and math libraries differ. This observation establishes portability of the assertion as a problem; it does not by itself prove either estimator value incorrect or validate every mathematical computation.
